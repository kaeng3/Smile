# 김일구 New스캐너 통합 설계

## 목표

`kaeng3/smile` GitHub Pages의 `베타 실험실 2`를 `김일구 New스캐너`로 교체한다. 평일 장 마감 후 KIS 일봉을 증분 갱신해 바닥권에서 당일 새로 `IGNITION` 또는 `BREAKOUT`으로 전환된 종목을 점수순 최대 5개까지 사이트와 텔레그램에 제공한다.

기존 실전 스캔, 베타 실험실 1·3, 기존 데이터와 자동화는 유지한다. 스캐너의 판단 결과는 후보 탐색 정보이며 주문 기능은 포함하지 않는다.

## 선택한 구조

스캐너의 실행에 필요한 Python 패키지, 설정, 실행 래퍼를 `smile` 저장소 안의 독립 폴더에 포함한다. 정적 GitHub Pages는 KIS를 직접 호출하지 않고, GitHub Actions가 생성한 JSON만 읽는다.

별도 저장소나 사용자 PC에 의존하는 구조는 사용하지 않는다. 이렇게 하면 사이트 코드와 결과 형식을 한 저장소에서 버전 관리할 수 있고, PC가 꺼져 있어도 실행된다.

## 저장소 구성

- `new_scanner/src/jusmo_scanner/`: 검증된 스캐너 엔진과 KIS 공급원
- `new_scanner/config/scanner.yaml`: Event 위치와 상태 판정 설정
- `new_scanner/requirements.txt`: 새 스캐너 전용 Python 의존성
- `new_scanner/run_daily.py`: 전 종목 증분 수집, TOP5 선정, 결과 저장, 텔레그램 발송 진입점
- `new_scanner/results/history.json`: 사이트가 읽는 최근 5영업일 결과
- `new_scanner/tests/`: 후보 선정, 결과 보관, 메시지, 중복 방지 테스트
- `.github/workflows/new_scanner.yml`: 장 마감 후 자동 실행과 Pages 재배포

스캐너의 원시 OHLCV 캐시, 토큰, SQLite 파일, 로그 및 `.env`는 Git에서 제외한다.

## 후보 선정 규칙

각 종목은 최근 3년 일봉으로 인과적으로 계산한다. 다음 조건을 모두 만족해야 후보가 된다.

1. 데이터의 마지막 봉이 실행 대상 거래일과 같다.
2. 기준 Event의 전략이 `BOTTOM_ACCUMULATION`이다.
3. 마지막 봉에서 상태가 새로 전환됐다.
4. 새 상태가 `IGNITION` 또는 `BREAKOUT`이다.
5. 상태가 `INVALIDATED`가 아니며 원가 판정이 `HOLD`다.
6. 거래정지·관리·정리매매 종목과 240봉 미만 종목은 제외한다.

통과 종목은 기존 `final_score` 내림차순으로 정렬하고, 동점이면 종목코드 오름차순으로 최대 5개를 선택한다. TOP5 밖의 종목은 화면이나 텔레그램에 포함하지 않는다. 후보가 없으면 빈 후보 목록을 정상 결과로 저장한다.

## 데이터와 증분 갱신

최초 실행은 현재 KOSPI·KOSDAQ 보통주 목록의 최근 3년 데이터를 수집한다. 이후 실행은 GitHub Actions 캐시에서 종목별 일봉을 복원하고 최근 10일 중복 구간과 신규 구간만 조회한다. 중복 구간의 수정주가·거래량이 달라지면 해당 종목의 최근 3년을 다시 수집한다.

Actions 캐시가 없거나 만료되면 전체 3년 수집으로 복구한다. 부분 수집 실패 종목은 그날 후보에서 제외하고 오류 개수만 결과 메타데이터에 기록한다. 전체 종목이 실패하거나 KIS 인증이 실패하면 새 결과를 게시하거나 텔레그램을 보내지 않고 작업을 실패 처리한다.

`history.json`은 날짜 내림차순으로 최대 5영업일을 보관한다. 각 날짜에는 실행 시각, 전체·성공·실패 종목 수, 후보 목록을 저장한다. 비밀키, 토큰, 계좌번호, 원시 API 응답은 저장하지 않는다.

## 사이트 화면

사이드바의 `🧪 베타 실험실 2`를 `🔎 김일구 New스캐너`로 바꾼다. 기존 `lab2` 탭 ID와 전환 함수는 유지해 다른 탭에 영향을 주지 않는다.

화면은 다음 요소로 구성한다.

- 최신 실행 기준일과 갱신 상태
- 최근 5영업일 날짜 선택 버튼
- TOP5 카드: 순위, 종목명·코드, `IGNITION/BREAKOUT`, 종가, 추정 매집원가, 원가 대비 비율, 최종점수
- 후보가 없는 날의 명시적 빈 상태
- JSON 로딩 실패 시 기존 사이트를 방해하지 않는 오류 안내
- 모바일에서는 카드가 한 열로 배치되는 반응형 레이아웃

화면에는 매수·매도 주문 버튼을 두지 않는다.

## 텔레그램

한 거래일의 TOP5를 메시지 한 개로 전송한다. 각 행에는 순위, 종목명·코드, 상태, 종가, 추정 매집원가, 원가 대비, 점수를 넣는다. 후보가 없으면 `오늘 신규 후보 없음`을 한 번 전송한다.

발송 성공 후에만 실행일을 발송 완료로 기록한다. 같은 날짜와 동일한 결과를 다시 실행하면 재발송하지 않는다. 발송 실패 시 완료 기록을 남기지 않아 다음 수동 재실행에서 다시 시도할 수 있게 한다. Telegram 오류에는 봇 토큰이나 원래 요청 URL을 포함하지 않는다.

## GitHub Actions와 비밀정보

새 워크플로는 평일 15:55 KST에 실행하고 수동 실행도 허용한다. 기존 Pages 작업과 같은 concurrency 그룹을 사용해 두 작업이 동시에 커밋·배포하지 않게 한다.

저장소 Secrets에는 다음 네 값이 필요하다.

- `KIS_APP_KEY`
- `KIS_APP_SECRET`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID`

워크플로는 테스트를 먼저 실행하고, 성공하면 스캔한다. 변경된 `history.json`만 커밋한 뒤 GitHub Pages를 재배포한다. 원시 캐시와 인증정보는 Actions 캐시에만 저장하고 커밋하지 않는다.

## 테스트와 검증

- 상태 전환이 없는 종목, 고점·중간권, `INVALIDATED`, 오래된 마지막 봉이 제외되는지 검증
- 점수 정렬, 동점 처리, 5개 제한 검증
- 최근 5영업일 롤링과 같은 날짜 재실행의 멱등성 검증
- 텔레그램 성공 후 기록, 실패 후 재시도, 비밀정보 비노출 검증
- `history.json` 스키마와 HTML의 필수 DOM·데이터 로딩 계약 검증
- 기존 `smile` 테스트와 스캐너 전체 테스트 실행
- 로컬 정적 서버에서 데스크톱·모바일 화면 확인
- Git 추적 파일과 배포 산출물에서 KIS·Telegram 비밀값 검사

## 배포 순서

1. 기능 브랜치에서 구현하고 로컬 미리보기와 테스트를 완료한다.
2. GitHub Secrets 네 값을 사용자 로그인 세션에서 등록한다.
3. 기능 브랜치를 GitHub에 올려 변경사항을 검토한다.
4. 확인 후 `main`에 반영한다.
5. 새 워크플로를 수동 실행해 최초 캐시와 사이트 결과를 생성한다.
6. GitHub Pages의 `김일구 New스캐너` 화면과 텔레그램 수신을 확인한다.

기존 `main`을 강제 푸시하거나 `db-seed` 브랜치를 변경하지 않는다.
